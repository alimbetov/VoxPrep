# 05 — Installation Security and Media Boundary

**Status:** FROZEN DESIGN INPUT

## 1. Installation identity

`installationId` is generated by Flutter once per app installation using a cryptographically secure random 128-bit UUID-v4-shaped value.

It identifies an app installation, not:

```text
person
account
physical device
phone number
IMEI
serial number
MAC address
advertising identifier
```

Hashing a hardware identifier does not make it acceptable identity.

Reinstall may create a new installationId.

## 2. Installation persistence

Backend conceptual record:

```text
Installation
├── installationId
├── status: ACTIVE | REVOKED
├── createdAt
├── lastSeenAt
├── tokenIssuedAt
└── currentTokenVerifier
```

Backend should not persist plaintext learner token if a verifier/hash design is available.

Secrets/tokens must never appear in logs, trace details or error responses.

## 3. Cold bootstrap

Every cold Flutter bootstrap performs:

```text
read/create stable installationId
→ POST /api/v1/installations
→ receive fresh installationToken
→ atomically replace previous local token
→ continue authenticated bootstrap/sync
```

A previously stored token does not skip fresh issuance.

## 4. Registration semantics

`POST /api/v1/installations` is replay-safe for the same installationId.

Backend may:

```text
create ACTIVE installation on first valid registration
rotate credential for existing ACTIVE installation
reject REVOKED installation
rate-limit abusive registration attempts
```

Re-registration must not fabricate a new installation identity.

## 5. Authorization

Learner protected endpoints use:

```http
Authorization: Bearer <installationToken>
```

Flutter application/business repositories do not manually own Authorization headers; the centralized transport/security layer does.

Backend validates the current token for the installation/security record.

## 6. Bounded 401 recovery contract

Flutter behavior:

```text
request with token A
→ 401
→ one single-flight re-issuance using same installationId
→ token B replaces A
→ safe request replayed once
→ second 401 = fail closed
```

Backend must support this deterministic behavior.

Concurrent requests rejected with the same stale token may converge on one client-side renewal operation.

Backend must not require more than one chained refresh endpoint or refresh-token protocol for MVP.

## 7. Revocation

REVOKED installation fails closed.

Expected semantics:

```text
protected request → 401/403 according to security policy
credential re-issuance → rejected
Flutter keeps installationId + learner local state
Flutter does not silently create another installationId to bypass revocation
```

## 8. Learner media boundary

The only CareerSpeak v1 media path is:

```text
Flutter
→ GET /api/v1/media/assets/{assetId}/content
→ Backend validates installation + publication/asset eligibility
→ Backend resolves FileAsset/deliveryKey internally
→ Backend reads RustFS
→ Backend streams bytes
→ Flutter verifies size + SHA-256
→ verified local file becomes usable
```

## 9. RustFS boundary

RustFS is private backend infrastructure.

Forbidden:

```text
Flutter receives RustFS endpoint
Flutter receives storage credentials
Flutter constructs bucket/object URLs
Flutter follows redirect to RustFS/S3
Flutter receives presigned storage URL in v1
TTS Worker receives RustFS credentials
TTS Worker writes PostgreSQL directly
```

Worker and Flutter communicate through Backend APIs only.

## 10. FileAsset model

Conceptual fields:

```text
assetId
mediaType
sizeBytes
checksumSha256
deliveryKey
storageStatus
createdAt
readyAt
```

`deliveryKey` is backend-internal and is not authorization data.

Asset readiness and publication eligibility are separate concerns.

## 11. Media authorization

Backend must verify that requested `assetId` is eligible for learner delivery.

Do not expose arbitrary RustFS object access by assetId alone if the asset is not associated with valid published content/current delivery rules.

Exact policy may be implemented through published-reference membership/indexes, but authorization outcome must be deterministic.

## 12. Media HTTP semantics

Flutter already classifies:

```text
2xx → success byte stream
401 → installation unauthorized
403 → media forbidden
404 → asset not found/not learner-visible
409 → asset not ready
408 → transient
429 → transient/rate limited
500/502/503/504 → transient
other rejection → non-retryable download rejection unless specified
```

Backend should return `Retry-After` for 429 where practical.

## 13. Integrity

Backend advertises:

```text
sizeBytes
checksumSha256
mediaType
```

Flutter verifies the exact bytes before atomically publishing a local cached file.

Checksum mismatch must never be treated as a successful download.

## 14. Security logging

Allowed audit metadata:

```text
installationId if privacy policy permits and it is necessary for security audit
traceId
endpoint
status
assetId
rate-limit/security decision
```

Never log:

```text
Authorization header
plaintext installationToken
RustFS secret/access key
raw backend storage credentials
sensitive exception dumps returned to clients
```

## 15. Explicit MVP non-goals

```text
learner username/password
OAuth/OIDC learner identity
refresh token
Keycloak learner realm
hardware attestation as primary identity
purchase entitlement verification
client-visible signed media delivery
```

Future device-integrity or entitlement signals may be added separately without replacing installationId semantics.
